# FIXES

Log of problems faced and how they were fixed, so any person or agent can avoid repeating them. Add a row whenever a problem is resolved and commit it with the change.

| PROBLEM | FIX | CAUSE / OCCUR | DATE |
| ------- | --- | ------------- | ---- |
| The production image shipped at 830MB carrying `typescript`, `vitest`, `ts-node-dev`, `eslint`, `prettier` and `supertest` | Added a `production-deps` stage running `npm ci --omit=dev`, and copy `node_modules` from there rather than from `build` | The production stage copied `node_modules` wholesale from the build stage, which had installed the full tree. The shortcut existed because `prisma generate` writes the client into `node_modules/.prisma`, so a plain `--omit=dev` install loses it. It is layered back in from the build stage. Occurs on every image build | 13-08-2026 |
| The lockfile was not enforced in the layer that shipped | Removed the dead `dependencies` stage. `npm ci` now runs in the two stages whose output is actually consumed | A `dependencies` stage ran `npm ci` and was then referenced by nothing, while `build` ran `npm install`, and production copied from `build`. Occurs on every image build | 13-08-2026 |
| The slimmed container exited 1 at boot with `unable to determine transport target for "pino-pretty"` | `logger.ts` resolves the module first and falls back to the JSON logger when it is absent | The logger requested the `pino-pretty` transport whenever `NODE_ENV` is `development`, but `pino-pretty` is a devDependency. Pino resolves the target lazily and throws at import time, killing the process before any route is registered. Hidden until the image stopped shipping dev dependencies, so the logger was always one `npm ci --omit=dev` away from this. Pinning `.env.container` to `production` was rejected as a fix, because it has to stay on `development` for the `DEV_TOKEN` bypass to work | 13-08-2026 |
| Test files and mocks were compiled into the production image | Added `tsconfig.build.json` excluding `src/tests`, and pointed the build script at it | `tsconfig.json` includes `src/**/*`, so every `.test.ts` was emitted to `dist` and copied in. Nothing requires them at runtime, so it never failed, it just shipped test code. The base config still covers the tests, so editor and typecheck support is unchanged. Occurs on every build | 13-08-2026 |
| Six integration tests answered 500 where they expected 200 or 401 | `globalSetup` now defaults `MONGO_URI` with credentials and `authSource=admin`, taking the user and password from `MONGO_ROOT_USER` and `MONGO_ROOT_PASSWORD` with the same fallbacks compose uses | The default was `mongodb://localhost:27017/Studzee_Database_Test`, which carries no credentials, while the compose Mongo runs with `MONGO_INITDB_ROOT_USERNAME` set. Mongoose connects lazily, so setup logged a successful connection and the failure appeared only on the first query as `MongoServerError: Command aggregate requires authentication`. That is why it presented as a server error rather than a connection error. Occurs on every integration run against the compose stack | 13-08-2026 |
| An unauthenticated request answered 500 instead of 401 | Set `CLERK_PUBLISHABLE_KEY` in `globalSetup` to a structurally valid test key, the base64 of a dummy Clerk domain | `NODE_ENV` is `test`, so the `DEV_TOKEN` bypass does not apply and the request reaches Clerk, which decodes the publishable key to find its API host and throws `Publishable key not valid` on `pk_test_placeholder`. The throw surfaced as a 500 before `requireAuth` could answer 401. The same root cause makes a container running with the placeholder keys in `.env.container` return 500 for unauthenticated requests | 13-08-2026 |
| A controller test asserted behaviour that should not exist | Removed the test and left a comment recording why, pointing at the integration test that covers the guarantee | `should check authentication before fetching document` expected `getDocumentById` to call `req.auth()`. It does not, and should not: `content.route.ts` guards the route with `clerkAuthMiddleware` and `requireAuth`, so anything reaching the controller is already authenticated. Satisfying the test would have meant adding redundant code to the controller | 13-08-2026 |
| New test files passed at runtime but did not compile | Fixed the fixtures to satisfy `ExpoSendResult`, replaced a top level `await import` with `vi.hoisted`, and cast the `NextFunction` mock. `npx tsc --noEmit -p tsconfig.json` is now a CI gate | Vitest transpiles without typechecking, so a test file can be green and still be wrong. Nothing in the pipeline checked, so this was invisible until typecheck was added. Occurs on any test file written against a partial type | 13-08-2026 |
| `npx vitest run` from the repository root failed every suite with `Cannot find package '@/...'` | Documented in TCSK and RULES that the suite runs from `BACKEND` only | The root has no `package.json` and no Vitest config, so npx installed an unrelated Vitest from the registry, no `@/*` alias resolved and `globalSetup` never ran. A root `package.json` was considered and rejected: MOBILE is an Expo app and Metro walks up the tree, so a stray root manifest risks breaking mobile module resolution. Occurs whenever the suite is run from the wrong directory | 13-08-2026 |
| The API could not run inside a container at all | Added `BACKEND/.env.container`, which addresses every dependency by its compose service name | `.env` and `.env.docker` both use `localhost`, which is correct for a host process but resolves to the container itself inside one. `prisma migrate deploy` runs before the app starts, so the container exits 1 with `P1001: Can't reach database server at localhost:5432` and never reaches any application code. Occurs on every attempt to run the image | 12-08-2026 |
| A containerized API reported `unhealthy` while serving traffic correctly | Set `PORT=3000` in `.env.container` so the app listens where the image expects, and publish `-p 4000:3000` | The Dockerfile declares `EXPOSE 3000` and its `HEALTHCHECK` probes port 3000, but every env file sets `PORT=4000`, so the probe failed with `ECONNREFUSED` on every interval. An orchestrator using `condition: service_healthy` would block or restart-loop a working service. Occurs on every container start | 12-08-2026 |
| `make seed`, `make logs` and `make refresh-cache` all fail | Documented as broken in the readme with the working npm equivalents alongside | They run `docker-compose exec api` or `docker-compose logs -f api`, and there is no `api` service in `docker-compose.yml`. Fails with `service "api" is not running`. Occurs on every invocation | 12-08-2026 |
| Storage troubleshooting in the readme told the reader to grep for `AWS` | Rewritten around the failures that actually occur, `NoSuchBucket`, `SignatureDoesNotMatch` and an unreachable public URL | The variables were renamed to `S3_*` during the Supabase move, so `cat .env \| grep AWS` returns nothing and the surrounding IAM advice applies to a provider no longer in use | 12-08-2026 |
| Clerk webhook signature verification could pass or fail by accident | Mounted the webhook router ahead of `express.json()` with `express.raw`, and verify the exact bytes. The handler now rejects a non Buffer body outright | The handler verified `JSON.stringify(req.body)` after the global JSON parser had already run. Re-serialising does not reproduce the original key order, whitespace or unicode escaping. Occurs on every Clerk delivery | 10-08-2026 |
| Push broadcast to more than 100 devices failed entirely | Chunk messages into batches of 100 in `expo.service.ts`. A failing batch no longer aborts the rest | Every token was posted to Expo in one request. Expo caps a request at 100 messages. Occurs on any broadcast once more than 100 devices are registered | 10-08-2026 |
| Retired push tokens accumulated and were counted as recipients | Read the Expo tickets, collect `DeviceNotRegistered` tokens, and prune them straight after the send | Ticket responses were never inspected and `checkExpoReceipts` was never called. Occurs whenever a user uninstalls the app | 10-08-2026 |
| Render keepalive never ran in production | Guard now skips only under test and requires `HEALTHCHECK_URL` | The job returned early unless `NODE_ENV === 'test'`, the inverse of the intent. Present in both services. Occurs in every deployed environment | 10-08-2026 |
| `PUT /admin/documents/:id` rejected every valid payload | Validate updates against `DocumentSchema.partial()` | A local schema demanded a string `content` and a `tags` field, neither of which exists on a document. Occurs on every document update | 10-08-2026 |
| Helmet CSP image directive resolved to the string `undefined` | Derive the bucket URL from validated config | The directive read `process.env.AWS_S3_BUCKET_URL`, a variable defined nowhere. Occurs on every response | 10-08-2026 |
| Importing `@/utils/logger` before `@/config` crashed at startup | Removed the module scope `logger.info` call from `config/s3.ts` | `config/index.ts` re-exports `s3.ts`, which logged at import time, while the logger imports config. Circular import left the logger undefined. Occurs whenever a module reaches the logger before it reaches config | 10-08-2026 |
| Prisma logged every SQL statement and its parameters in production | Query logging is development only | The client was constructed with `log: ['query', ...]` unconditionally. Occurs on every query in every environment | 10-08-2026 |
| Email attachments could be fetched from any URL | Attachment URLs must be https on a host in `EMAIL_ATTACHMENT_HOSTS`, capped at 10 per message | Nodemailer fetches an attachment given as a `path`, and the value came straight from the admin request with no checks. Occurs on any email send with attachments | 10-08-2026 |
| Broadcast emails disclosed the whole recipient list | Recipients moved to `bcc` | Every address was passed in `to` and joined into one header. Occurs on any multi recipient send | 10-08-2026 |
| `npm run seed` emptied the database and seeded nothing, reporting success | Converted the fixture in `src/data/data.json` to the structured section form, and made the script exit non-zero when any document fails validation | The fixture still carried `content` as a single prose string from v1, which `DocumentSchema` rejects because content is structured. The script cleared the collection first, so a run left the database empty while logging "Successfully seeded 0 documents" and exiting 0. Occurs on every seed | 11-08-2026 |
| Seed validation errors were logged with no reason attached | Pass the context object first, as Pino expects | The call was `logger.error('Invalid document:', errors)`. Pino takes the object first and the message second, so the errors were silently discarded and every failure printed a bare "Invalid document:" | 11-08-2026 |
| Local uploads would fail because MinIO had no buckets | A one-shot `minio-init` container creates `images`, `pdfs` and `assets` and marks each publicly readable once MinIO is healthy | The env files named the buckets but nothing created them, and MinIO creates none on its own. The readme told a developer to create one bucket by hand, which was manual and out of date. Occurs on the first upload in any fresh checkout | 11-08-2026 |
| Uploads targeted one bucket with key prefixes, but the project has three buckets | Split into `S3_BUCKET_IMAGES` and `S3_BUCKET_PDFS`, and made the upload service select a bucket rather than prepend a prefix | The Supabase project is laid out as separate `images`, `pdfs` and `assets` buckets. The code wrote `images/<file>` into a single bucket, which does not exist, so every upload would have failed. Found by listing the buckets with the real credentials rather than assuming | 11-08-2026 |
| Object storage was unusable against any non AWS provider | `forcePathStyle` and the endpoint are applied unconditionally, and the public URL base is configured through `S3_PUBLIC_URL` rather than derived | `forcePathStyle` and the endpoint were applied only when `NODE_ENV=development`, and the public URL was built in the AWS virtual-hosted form. Supabase and MinIO both address buckets as a path segment and serve public objects from a different host to their S3 endpoint. Occurs on every upload and delete once the provider is Supabase | 11-08-2026 |
| `getKeyFromUrl` returned the wrong key for a Supabase URL | Strip the configured public base, with a trailing `<folder>/<filename>` fallback for URLs stored under a previous provider | It returned the whole URL path, which on Supabase is `storage/v1/object/public/<bucket>/...` rather than the key. Occurs on every image replacement, which deletes the old object by key | 11-08-2026 |
| Readiness reported healthy during a Postgres outage | Probe MongoDB, Postgres and Redis, and fail the check if any one of them fails | The endpoint only checked Mongo and Redis. | Readiness could report healthy against a dead socket | Each probe now issues a real round trip: `admin().ping()`, `SELECT 1` and `PING`, in parallel with a 2 second timeout each | The check read `mongoose.connection.readyState` and `redisClient.isOpen`, which report what the driver believes about its socket rather than whether the server answers. | `KEYS` blocked the Redis event loop during cache invalidation | Replaced with a cursor based `SCAN` loop | `redisClient.keys()` traverses the whole keyspace in one blocking call. Occurs on every admin write | 10-08-2026 |
